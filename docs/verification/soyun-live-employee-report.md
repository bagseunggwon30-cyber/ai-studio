# 업무일지·회의실·완성작 개선 검토

> 작성: 리서치·문서 담당 · 요청 작업: T0015 · 작성일: 2026-10-03

## 결론 요약

작은 패널 구조 개선으로 업무일지의 기록 누락과 긴 문장 가독성, 회의실의 후보·질문·결과 구분, 완성작 목록의 6개 제한을 함께 해결할 수 있다. 업무일지는 전체 기록을 스크롤 목록으로 보여주고 긴 문장을 줄바꿈하며, 회의실은 모든 후보·질문·결재 결과를 선택 상태와 구분해 한 화면 흐름에 둔다. 완성작은 6칸 고정 배치를 데이터 기반 전체 목록으로 바꿔 7번째 이후 항목까지 계속 탐색할 수 있게 한다. 기존 그림 분위기, `textContent` 기반 문자열 처리, CSP self, Esc·포커스 복귀·키보드 동작과 결재·재기획·문서열기·게임실행 흐름을 유지하는 것을 완료 기준으로 삼는다. 아래 UI 관찰은 감독자 전달 사항이며, 제안한 기준과 화면 시험은 구현 후 검토 항목이다.

## 핵심 주장

1. 감독자 전달 사실에 따르면 업무일지는 `events.slice(0,8)`로 기록을 제한하고 긴 문장을 한 줄로 표시하므로, 전체 기록 탐색과 줄바꿈이 우선 개선 대상이다. UI를 독립적으로 확인한 관찰은 아니다. [S1][S4]
2. 감독자 전달 사실에 따르면 회의실은 후보를 최대 8개 보이고 질문을 별도 버튼 뒤에 숨기며 선택 수와 결재 동작을 제공한다. 후보·질문·선택·결과를 분리해 표시하면 과정의 의미와 키보드 이동 순서를 함께 확인하기 쉽다. [S1][S2]
3. 감독자 전달 사실에 따르면 완성작은 6칸만 생성한다. 고정 칸 대신 자료 수만큼 렌더링하는 목록을 제안한다. WCAG reflow는 일반 콘텐츠가 좁은 뷰포트에서도 읽히도록 하되, 고정 크기 캔버스처럼 크기 유지가 의미에 필요한 UI는 예외적 고려가 있을 수 있다고 설명한다. 이 스테이지가 해당 예외에 해당하는지는 별도 확인이 필요하다. [S3]
4. WCAG는 키보드로 기능을 조작할 수 있고, 순차 포커스가 의미와 조작성을 보존해야 한다고 설명한다. 제안된 포커스·Esc·복귀 기준은 팝업 사용자 흐름에 이를 적용한 검증 기준이다. [S1][S2]
5. 긴 텍스트의 줄바꿈과 오버플로 처리는 CSS `overflow-wrap` 등으로 다룰 수 있고, 동적 일반 문자열은 기존 `textContent` 방식을 유지하는 편이 안전하다. [S4][S5]

## 상세

아래 개선안은 감독자가 전달한 구조 정보를 토대로 한 구현 검토 제안이다. 화면의 현재 배치나 동작을 직접 관찰한 결과가 아니다.

### 업무일지

- **개선안:** 기존 그림 스타일과 패널의 외곽·색·장식은 유지한다. 기록은 최신/기존 순서를 명확히 표시하는 단일 스크롤 영역에 전부 렌더링하고, 상단에 총 기록 수를 둔다. 한 항목에는 날짜/구분과 본문을 나누어 두며, 긴 문장·긴 URL은 자연스럽게 여러 줄로 흐르게 한다. 가로 폭을 늘려야만 읽을 수 있는 한 줄 고정·말줄임은 피한다. [S4]
- **완료 기준:** 기록이 0개, 8개, 9개, 다수인 경우 모두 데이터 개수와 표시 개수가 일치한다. 긴 문장 및 공백 없는 긴 문자열도 패널 밖으로 잘리거나 옆 항목과 겹치지 않는다. 목록 내부에서 세로 스크롤할 수 있고, Tab 순서가 목록 앞뒤의 실제 조작 순서를 따르며 Esc로 닫은 뒤 팝업을 열었던 컨트롤에 포커스가 돌아온다. [S1][S2][S4]
- **시험 순서:** 기록이 0개인 상태에서 빈 상태 문구를 확인한다 → 8개/9개/다수 기록을 넣어 첫 항목부터 마지막 항목까지 개수와 순서를 확인한다 → 긴 한국어 문장, 매우 긴 영문/URL을 확인한다 → 키보드만으로 열기·목록 탐색·닫기를 수행하고 포커스 표시, Esc 닫기, 원래 버튼으로의 복귀를 확인한다.

### 회의실

- **개선안:** 후보 카드는 8개에서 끊지 말고 전부 탐색 가능한 목록으로 표시한다. 각 후보에는 식별 가능한 제목과 선택 상태를 둔다. 질문은 별도 버튼 뒤에만 감추지 말고 후보와 연관된 질문 영역 또는 목록에 바로 확인 가능한 요약·본문으로 둔다. 선택 수와 선택 가능한 수를 읽을 수 있게 표시하고, 결재 전 선택 상태와 결재 후 결과/상태를 시각적으로 다른 영역으로 구분한다. 한 패널 안에서 `후보 → 질문/검토 → 선택 현황 → 결재 결과` 순서를 유지한다. [S1][S2]
- **완료 기준:** 후보 0개, 1개, 8개, 9개 이상 모두 전체가 나타나며, 각 질문이 맞는 후보와 연결된다. 키보드로 각 후보의 선택/해제를 할 수 있고 선택 수가 실제 상태와 맞는다. 결재 동작은 기존 조건과 결과를 유지하며, 결과가 선택 UI와 구별된다. 질문, 선택, 결재 버튼 간 Tab 이동이 논리적이고 포커스가 가려지지 않으며, Esc로 닫았을 때 초점을 호출 컨트롤로 돌린다. [S1][S2]
- **시험 순서:** 후보 0개 및 1개를 확인한다 → 8개와 9개 이상을 열어 처음·중간·마지막 후보와 질문을 확인한다 → 키보드로 선택/해제를 섞어 선택 수를 대조한다 → 기존 결재 조건을 충족해 결재하고, 기존 거절/미충족 조건의 안내도 확인한다 → 결재 이후 결과 표시와 후속 재기획·문서열기·게임실행 흐름을 실행해 회귀 여부를 본다 → Esc와 포커스 복귀를 확인한다.

### 완성작

- **개선안:** 여섯 개의 고정 칸 생성 대신 보유 데이터의 각 완성작을 전부 나열하는 반응형 목록/그리드로 렌더링한다. 카드에는 제목과 구분 가능한 요약을 두고, 항목별 기존 동작이 있다면 해당 동작을 유지한다. 패널을 길게 만들기보다 내부 세로 스크롤을 제공하되 마지막 항목까지 도달할 수 있게 한다. [S2][S3]
- **완료 기준:** 0개, 1개, 6개, 7개, 그 이상의 항목에서 데이터 수와 보이는 탐색 항목 수가 일치하며, 7번째 및 마지막 항목도 스크롤로 도달·식별할 수 있다. 키보드 포커스는 항목의 읽기 순서와 일치하고 마지막 항목 뒤의 닫기 컨트롤로 빠져나올 수 있다. Esc 닫기와 호출 지점으로의 포커스 복귀가 유지된다. [S1][S2]
- **시험 순서:** 0/1/6/7/다수 항목으로 상태를 바꿔 수량과 순서를 확인한다 → 맨 아래까지 스크롤해 마지막 카드와 동작을 확인한다 → 키보드만으로 첫 항목부터 마지막 항목 및 닫기까지 이동한다 → 항목 동작, Esc, 포커스 복귀를 확인한다.

### 공통 구현·검토 기준

- 기준 스테이지 1536×1024에서 기존 그림 분위기와 팝업 맥락을 유지하고, 목록이 길어져도 패널 제목·닫기 및 주요 조작부를 찾을 수 있게 한다. WCAG reflow 설명에 맞춰 데스크톱 브라우저 확대 시에도 내용 누락·가림이 없는지 점검하되, 고정 크기 스테이지의 적합성 여부는 현재 자료로 판정하지 않는다. 모바일은 별도 `/m` 화면이므로 이번 세 팝업 변경과 섞지 않는다. 필요 시 회귀 확인은 별도 항목으로 기록한다. [S3]
- 동적 문자열은 `textContent` 기반으로 처리한다. `textContent` 설정은 대상 노드의 자식 노드를 문자열 텍스트 노드 하나로 교체하므로, 조작 버튼 등 내부 구조를 보존해야 하는 요소에 통째로 대입하지 않는지 구현에서 확인한다. `innerHTML`로 동적 문자열을 조립하지 않는다. [S4]
- CSS overflow는 내용이 박스 밖으로 나올 때 스크롤 영역 등으로 다룰 수 있으며, `overflow-wrap`은 끊을 수 없는 긴 문자열의 줄바꿈에 사용할 수 있다. 적용한 스크롤이 키보드로도 접근 가능하고 마지막 내용까지 보이는지 실제 스테이지에서 확인한다. [S5]
- 정적 HTML/CSS/JS 범위 안에서 CSP self를 유지한다. 새 외부 스크립트·스타일·폰트나 새 의존성을 전제로 하지 않는다. 실제 화면 시험은 먼저 1536×1024 기준으로 수행하고, 이후 브라우저 확대/축소 시 제목·닫기·내용·주요 버튼이 가려지거나 사라지지 않는지 확인한다.
- 세 패널 각각에서 포커스 표시, 순서, Esc 닫기, 닫은 뒤 호출 지점 복귀를 확인한다. 포커스 순서 기준은 WCAG 설명에 근거하며, WCAG 준수 여부 전체를 이 검토 하나로 선언하지 않는다. [S1][S2]

## 우리에게 적용

- 권고: 구현 작업에서 위 각 화면의 완료 기준을 수용 체크 항목으로 사용하고, 특히 데이터 경계(0/8/9 및 6/7 이상)와 긴 텍스트를 대표 시험 자료로 고정한다.
- 권고: 변경 전후로 그림 분위기와 1536×1024 스테이지를 비교하고, 키보드 전용 시나리오를 세 화면 모두 실행한다. 결재/재기획/문서열기/게임실행은 시험 계정 또는 안전한 로컬 상태에서 실제 결과까지 대조한다.
- 이번 문서는 검토 보고서이며 로컬 구현이나 브라우저 확인을 수행하지 않았다. 아래 화면 시험 절차의 실행 결과는 구현자가 따로 기록해야 한다.
- 보고서는 허용 경로인 `reports/connection-check/` 아래 신규 중첩 파일이다. 자동 QA가 `reports/` 루트 파일만 검사하는 한계가 작업 카드에 명시되어 있으므로, 이 문서의 형식·주장·제안이 의미상 맞는지 별도 검토하고 실제 UI 검증도 따로 수행해야 한다. 루트 파일 자동 검사의 통과 여부를 이 보고서의 검증으로 간주하지 않는다.

## 미확인·한계

- **원문 소스 확인 실행 안 함:** `ui/popups.js`를 직접 열거나 구현을 대조하지 않았다. 팝업 개수 제한·표시·흐름 정보는 감독자가 전달한 사실이다.
- **브라우저/실제 UI 시험 실행 안 함:** 제안한 완료 기준과 시험 절차는 구현 후 확인할 항목이다. 현재 화면의 치수·색상·포커스 처리·결재 결과를 확인하지 않았다.
- **자동 QA 제한:** 감독자 전달에 따라 자동 QA가 `reports/` 루트 파일만 검사할 수 있다. 중첩 경로 보고서의 자동 확인 여부는 [미확인]이며, 의미 검토와 실제 UI 검증은 별도로 필요하다.
- **해석의 범위:** WCAG 출처는 일반 키보드 조작·포커스 순서·reflow 기준이고, 업무일지/회의실/완성작에 관한 제안은 이를 전달된 화면 조건에 적용한 권고다. 보고서만으로 해당 UI의 WCAG 적합성이나 모바일 화면 동작을 판정할 수 없다.
