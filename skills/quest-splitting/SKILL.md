### 순서
1. 지시를 한 문장 목표로 다시 쓴다. 모호한 곳(재미, 아트 방향, 출시, 우선순위)은 추측하지 말고 questions에 쓴다.
2. 프로젝트 정보(파일 목록, `docs/INTERFACES.md`, `docs/GAME_BRIEF.md`)와 '진행 중·대기 중', '최근 완료' 목록을 읽는다. 이미 있거나 진행 중인 일을 다시 만들지 않는다.
3. 관찰할 수 있는 변화 하나씩 퀘스트로 나눈다. 퀘스트 하나는 파일 1~5개, 에이전트 한 번(20분)에 끝낼 크기다.
4. 지시가 크면 첫 단계만 퀘스트로 만들고, 나머지는 summary에 '다음 단계'로 쓴다.
5. 순서가 꼭 필요한 것만 depends_on으로 잇는다 (이 목록 안에서 0부터 세는 번호). 서로 다른 파일을 건드리는 일은 잇지 않는다.

### 카드 한 장 채우기
- title: 무엇이 바뀌는지 보이게 (예: "HUD에 남은 시간 표시"). "개선", "정리"처럼 흐린 말은 쓰지 않는다.
- kind: 코드·파일을 바꾸면 `build`, 조사해서 보고서를 쓰면 `research` (보고서는 Studio Docs의 `reports/`).
- brief: 무엇을 왜 하는지, 어느 파일·함수를 기준으로 하는지. 계약 문서가 있으면 "계약(이름·인자·상수)을 바꾸지 않는다"를 쓴다.
- acceptance: 확인할 수 있는 문장 2~4개. 신뢰 테스트 이름, 파일에 있어야 할 것, 화면에 보일 것. "잘 동작한다"는 쓰지 않는다.
- allowed_paths: 필요한 폴더만 좁게 (`src/world/**`, `scenes/main.tscn`). 새 입력 동작이 필요하면 `project.godot`도 넣는다. `acceptance/`, `AGENTS.md`, `.gitignore`는 넣지 않는다.
- difficulty: 1 작고 분명함, 2 보통, 3 여러 파일이나 판단이 필요함.

### 흔한 실수
- 한 카드에 규칙·화면·소리를 몰아넣기 → 관찰할 수 있는 변화 하나씩 나눈다.
- 허용 경로를 저장소 전체(`**`)로 주기 → 필요한 폴더만 준다.
- 신뢰 테스트나 계약 문서를 바꾸는 카드 → 만들지 않고 questions에 쓴다.
- 리서치 카드에 개발 일을 섞기 → 따로 나눈다.
- 앞 카드가 끝나야만 할 수 있는데 depends_on을 빼기 → 같은 파일이나 앞 카드의 결과를 쓰면 잇는다.

### 확인
- 카드 수가 설정의 최대 개수 이하인가.
- 카드 한 장만 읽어도 무엇을 해야 하는지 분명한가.
- depends_on 번호가 목록 안에 있고, 서로 돌고 도는 의존이 없는가.
- skills_used에 이번에 따른 배운 스킬을 적었는가 (이 스킬을 따랐으면 `quest-splitting`).
